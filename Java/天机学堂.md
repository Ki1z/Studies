## 项目环境搭建

### 企业开发模式

微服务项目相比传统项目，包含的项目模块非常多，每个模块都需要独立部署，因此在开发模式上有很大差别，开发人员数量成倍增多，分组分别开发不同的微服务模块，微服务模块间有业务关联，需要相互协作

而我们当前的天机学堂项目开发情况如下

> ![](javaweb2/239.png)

其中绿色勾表示已经开发完成，黄色圆圈表示正在开发中，红色叉表示暂未开发

而我们在企业中开发时，不同的服务代码一般位于不同的仓库中，作为某一个微服务的开发人员，我们是没有权限拉取和推送代码到其他仓库的。而且微服务的运行环境非常复杂，比如先前的黑马商城项目，我们需要同时启动Nacos、Sentinel、Seata、Redis、MySQL、RabbitMQ等等，因此本地部署的难度也较高

但是如何进行远程调用测试呢？在企业开发中，针对测试有不同的测试阶段：

- 单元测试：测试最小的可测试单元
- 集成测试：验证某个功能接口
- 组件测试：验证微服务组件
- 端对端联调：验证整个系统

单元测试和集成测试是在本地完成的，如果需要测试远程调用，一般企业会准备一套远程公共Mock服务来测试远程调用接口，也就不需要其他尚未开发完成的实际接口

### 持续集成环境

不难发现，在上文的虚拟机中，并没有启动已经开发完成的微服务，这里就需要引出持续集成环境。持续集成是一种DevOps软件开发实践，DevOps中Dev为Develop，Ops为Operation，即开发与运维，也就是让开发与运维间更加流畅，打破开发与运维间的隔阂。例如我们在开发完成后，需要将代码进行打包、发布、编译、构建、部署等等，如果人为操作就非常麻烦，而且也及其容易出错

而持续集成可以自动构建、发布、测试，同时防止主干和分支存在较大差异，快速发现错误，并解决错误。而天机学堂项目中，也引入了持续集成环境，分别是Jenkins，负责编译，构建，测试代码；Gogs，负责代码托管，也就是Git私服；以及Docker，负责部署，Docker可以利用dockerfile和docker-compose快速部署。在这套持续集成环境中，只需要程序员在IDE中点击提交按钮，代码由Gogs接管，然后通知Jenkins拉取并编译、构建，然后打包为Docker镜像，最后Docker自动部署，程序员只需要关注中间步骤是否出错，以及访问最后运行的容器

### BUG修复

很明显这里存在一个业务BUG，可能的原因有两点，第一，删除订单时真的获取到了别人的订单id，所以导致鉴权失败；第二，鉴权出现问题，获取订单id正确，但是在判断订单归属时出现错误，导致后台认为该订单属于其他用户

不过，解决BUG并不是目的，解决这个BUG的最终目的是学会阅读项目代码、学会定位问题、分析问题，学会发布代码到开发环境，以及熟悉项目结构

```java
public void deleteOrder(Long id) {
    // 1.获取登录用户
    Long userId = UserContext.getUser();
    // 2.查询订单
    Order order = getById(id);
    if (order == null) {
        return;
    }
    // 3.判断订单所属用户与当前登录用户是否一致
    if(userId != order.getUserId()){
        // 不一致，说明不是当前用户的订单，结束
        throw new BadRequestException("不能删除他人订单");
    }
    // 4.删除订单
    boolean success = removeById(id);
    if (!success) {
        throw new DbException(OPERATE_FAILED);
    }
}
```

从上往下看，首先获取登录用户，然后查询订单，再判断订单所属用户与当前登录用户是否一致。这里就出现了我们在测试时遇到的报错throw new BadRequestException("不能删除他人订单")。所以问题一定出现在if(userId != order.getUserId())，这也与我们最初的推测一致，要么删除订单时真的获取到了别人的订单id，所以导致鉴权失败；要么获取订单id正确，但是在判断订单归属时出现错误，导致后台认为该订单属于其他用户。这里只要userId或者order.getUserId()任意一个获取错误，都会导致报错

但仔细思考一下，哪一个出错的概率更大呢？order.getUserId()来源于我们用订单id获取到的订单实体中的用户id，理论上来说，这里出错的概率应该比较小才对，如果order.getUserId()都出错了，则说明数据库在保存订单数据时就出错了，订单id无法正确对应用户id。但从另一个角度上来说，我们登录不用的用户，却又能获取到不同的订单数据，这与前面的推测矛盾。所以我们将目光着重于userId，userId来自于Long userId = UserContext.getUser()，我们进行跟踪

```java
package com.tianji.common.utils;

public class UserContext {
    private static final ThreadLocal<Long> TL = new ThreadLocal<>();

    /**
     * 保存用户信息
     * @param userId 用户id
     */
    public static void setUser(Long userId){
        TL.set(userId);
    }

    /**
     * 获取用户
     * @return 用户id
     */
    public static Long getUser(){
        return TL.get();
    }

    /**
     * 移除用户信息
     */
    public static void removeUser(){
        TL.remove();
    }
}
```

可以看到UserContext仅仅是利用ThreadLocal保存了用户信息，UserContext.getUser()本身也不存在什么问题。那么问题出在哪儿呢？重新模拟一下BUG出现的过程。首先jack进行登录，然后由UserContext.getUser()获取到jack的id，再使用订单id获取订单实体，用订单实体中的用户id与jack的Id进行比较，比较通过，因此删除成功；然后rose进行删除，UserContext.getUser()先获取用户id。这里就不难发现，UserContext.getUser()获取的到底是jack的id，还是rose的Id呢？接下来不再进行推测，而是直接进行测试验证

#### 解决问题

结果显而易见，正是因为使用了基本比较符!=，所以导致比较出错。而出错的根本是Java对于数值包装类的设定。Java对整数包装类设计了缓存机制，默认缓存-128到127的整数包装类型，而\=\=或者!=比较符并不是数值比较，而是引用比较，在内存中，缓存外的包装类数值占用不同的内存空间，因此\=\=或者!\=比较的结果为false，导致程序出现BUG

我们可以跟踪到Long的valueOf方法

```java
@HotSpotIntrinsicCandidate
public static Long valueOf(long l) {
    final int offset = 128;
    if (l >= -128 && l <= 127) { // will cache
        return LongCache.cache[(int)l + offset];
    }
    return new Long(l);
}
```

这里执行了一个判断，当传入的long l在-128到127之间时，会直接返回LongCache.cache数组中的值，否则返回一个新对象

```java
private static class LongCache {
    private LongCache(){}

    static final Long cache[] = new Long[-(-128) + 127 + 1];

    static {
        for(int i = 0; i < cache.length; i++)
            cache[i] = new Long(i - 128);
    }
}
```

问题已经溯源，解决方法也很简单，使用Objects类中的equals方法，它首先会进行==比较，然后还会调用对象自身的equals方法来比较，而Long的equals方法如下

```java
public boolean equals(Object obj) {
    if (obj instanceof Long) {
        return value == ((Long)obj).longValue();
    }
    return false;
}
```

调用了longValue()方法，longValue()返回的是一个long基本类型，因此可以保证比较结果正确。所以，我们将源代码进行更正

```java
// 3.判断订单所属用户与当前登录用户是否一致
if(!Objects.equals(userId, order.getUserId())){
    // 不一致，说明不是当前用户的订单，结束
    throw new BadRequestException("不能删除他人订单");
}
```

```java
@Override
@Transactional
public PlaceOrderResultVO enrolledFreeCourse(Long courseId) {
    Long userId = UserContext.getUser();
    // 1.查询课程信息
    List<Long> cIds = CollUtils.singletonList(courseId);
    List<CourseSimpleInfoDTO> courseInfos = getOnShelfCourse(cIds);
    if (CollUtils.isEmpty(courseInfos)) {
        // 课程不存在
        throw new BizIllegalException(TradeErrorInfo.COURSE_NOT_EXISTS);
    }
    CourseSimpleInfoDTO courseInfo = courseInfos.get(0);
    if(!courseInfo.getFree()){
        // 非免费课程，直接报错
        throw new BizIllegalException(TradeErrorInfo.COURSE_NOT_FREE);
    }
    // 2.创建订单
    Order order = new Order();
    // 2.1.基本信息
    order.setUserId(userId);
    order.setTotalAmount(0);
    order.setDiscountAmount(0);
    order.setRealAmount(0);
    order.setStatus(OrderStatus.ENROLLED.getValue());
    order.setFinishTime(LocalDateTime.now());
    order.setMessage(OrderStatus.ENROLLED.getProgressName());
    // 2.2.订单id
    Long orderId = IdWorker.getId(order);
    order.setId(orderId);

    // 3.订单详情
    OrderDetail detail = packageOrderDetail(courseInfo, order);

    // 4.写入数据库
    saveOrderAndDetails(order, CollUtils.singletonList(detail));

    // 5.发送MQ消息，通知报名成功
    rabbitMqHelper.send(
            MqConstants.Exchange.ORDER_EXCHANGE,
            MqConstants.Key.ORDER_PAY_KEY,
            OrderBasicDTO.builder()
                    .orderId(orderId)
                    .userId(userId)
                    .courseIds(cIds)
                    .finishTime(order.getFinishTime())
                    .build()
    );
    // 6.返回vo
    return PlaceOrderResultVO.builder()
            .orderId(orderId)
            .payAmount(0)
            .status(order.getStatus())
            .build();
}
```

```java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.time.LocalDateTime;

import java.util.List;

@Service
@Slf4j
@RequiredArgsConstructor
public class LessonServiceImpl implements LessonService {

    private final LessonMapper lessonMapper;
    private final CourseClient courseClient;

    @Override
    @Transactional
    public void addLessonsInBatch(List<Long> courseIds, Long userId) {
        log.info("用户{}添加课程{}的课表", userId, courseIds);
        // 1.获取课程信息
        List<CourseSimpleInfoDTO> courseInfos = courseClient.getSimpleInfoList(courseIds);
        // 验证课程信息
        if (courseInfos == null || courseInfos.isEmpty())
            throw new BadRequestException("课程不存在");

        List<LearningLesson> lessons = new ArrayList<>(courseInfos.size());
        // 2.遍历课程信息
        for (CourseSimpleInfoDTO courseInfo : courseInfos) {
            // 3.计算过期时间
            Integer validDuration = courseInfo.getValidDuration();
            // 如果课程没有有效期，则过期时间为null
            // validDuration单位为月
            LocalDateTime expireTime = validDuration == null ? null : LocalDateTime.now().plusMonths(validDuration);
            // 4.向lessons插入实体
            lessons.add(LearningLesson.builder()
                    .id(IdWorker.getId())
                    .courseId(courseInfo.getId())
                    .userId(userId)
                    .expireTime(expireTime)
                    .build()
            );
        }
        // 5. 批量插入
        Integer columns = lessonMapper.addLessonsInBatch(lessons);
        // 6. 判断插入是否成功
        if (columns == 0 || columns != courseIds.size())
            throw new DbException("添加课程失败");
    }
}
```

#### 分页查询我的课表

在开发接口之前，我们需要知道，当前登录用户的信息从何而来，所以我们模拟一下用户登录过程

天机学堂是一个微服务项目，所以用户的请求首先发往网关，再由网关路由到各个微服务，而用户登录凭证也会随之进行路由。在黑马商城项目中，我们便使用了以JWT令牌为基础的用户身份认证技术，用户在登录成功后，由后端下发一个JWT令牌，而后用户请求其他页面内容时，需要携带这个JWT的Token，这个Token通过网关进行认证，然后将用户凭证下发到各个微服务，微服务就能知道用户信息

所以接下来我们追踪一下源码，来研究一下天机学堂的用户登录过程是如何完成的。首先定位到网管微服务中的自定义拦截器

```java
package com.tianji.gateway.filter;

import com.tianji.authsdk.gateway.util.AuthUtil;
import com.tianji.common.domain.R;
import com.tianji.common.domain.dto.LoginUserDTO;
import com.tianji.gateway.config.AuthProperties;
import org.springframework.cloud.gateway.filter.GatewayFilterChain;
import org.springframework.cloud.gateway.filter.GlobalFilter;
import org.springframework.core.Ordered;
import org.springframework.http.server.reactive.ServerHttpRequest;
import org.springframework.stereotype.Component;
import org.springframework.util.AntPathMatcher;
import org.springframework.web.server.ServerWebExchange;
import reactor.core.publisher.Mono;

import java.util.List;

import static com.tianji.auth.common.constants.JwtConstants.AUTHORIZATION_HEADER;
import static com.tianji.auth.common.constants.JwtConstants.USER_HEADER;

@Component
public class AccountAuthFilter implements GlobalFilter, Ordered {

    private final AuthUtil authUtil;
    private final AuthProperties authProperties;
    private final AntPathMatcher antPathMatcher = new AntPathMatcher();

    public AccountAuthFilter(AuthUtil authUtil, AuthProperties authProperties) {
        this.authUtil = authUtil;
        this.authProperties = authProperties;
    }

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        // 1.获取请求request信息
        ServerHttpRequest request = exchange.getRequest();
        String method = request.getMethodValue();
        String path = request.getPath().toString();
        String antPath = method + ":" + path;

        // 2.判断是否是无需登录的路径
        if(isExcludePath(antPath)){
            // 直接放行
            return chain.filter(exchange);
        }

        // 3.尝试获取用户信息
        List<String> authHeaders = exchange.getRequest().getHeaders().get(AUTHORIZATION_HEADER);
        String token = authHeaders == null ? "" : authHeaders.get(0);
        R<LoginUserDTO> r = authUtil.parseToken(token);

        // 4.如果用户是登录状态，尝试更新请求头，传递用户信息
        if(r.success()){
            exchange.mutate()
                    .request(builder -> builder.header(USER_HEADER, r.getData().getUserId().toString()))
                    .build();
        }

        // 5.校验权限
        authUtil.checkAuth(antPath, r);

        // 6.放行
        return chain.filter(exchange);
    }

    private boolean isExcludePath(String antPath) {
        for (String pathPattern : authProperties.getExcludePath()) {
            if(antPathMatcher.match(pathPattern, antPath)){
                return true;
            }
        }
        return false;
    }

    @Override
    public int getOrder() {
        return 1000;
    }
}
```

在天机学堂项目中，定义了一个AccountAuthFilter，实现了GlobalFilter和Ordered，GlobalFilter用于实现拦截，Ordered用于排序。在filter方法中，首先通过exchange.getRequest()获取原始请求，然后获取请求方法和请求路径，拼接为`请求方法:请求路径`的形式，并传入isExcludePath方法，与排除路径进行匹配，如果该路径为排除路径，则直接放行。接着从请求头中获取权限字段，天机学堂中使用的字段为public static final String AUTHORIZATION_HEADER = "authorization"，然后传入AuthUtil的parseToken方法进行验证。parseToken返回一个自定义通用响应类R，通过调用R的success方法来判断解析是否正确，如果解析正确，则更新请求头字段，将用户信息保存在请求头中。此时再进行权限验证

```java
public void checkAuth(String antPath, R<LoginUserDTO> r){
    // 1.判断是否是需要权限的路径
    String matchPath = findMatchPath(antPath);
    if(matchPath == null){
        // 没有权限限制，直接放行
        return;
    }
    // 2.判断是否登录成功
    if(!r.success()){
        // 未登录，直接报错
        throw new UnauthorizedException(r.getCode(), r.getMsg());
    }
    // 3.获取当前路径所需权限
    PrivilegeRoleDTO pathPrivilege = findPathPrivilege(matchPath);

    // 4.权限判断
    Set<Long> requiredRoles = pathPrivilege.getRoles();
    if (!CollectionUtil.contains(requiredRoles, r.getData().getRoleId())) {
        // 没有访问权限
        throw new ForbiddenException(FORBIDDEN);
    }
}
```

这里可能产生一些疑问，为什么先传递用户信息，再进行权限验证？实际上，我们可以大致理解为，天机学堂希望用户信息的传递不受权限验证的约束，因为用户登录与用户拥有指定权限是两件事，在严格的权限管理项目中，用户拥有不同的身份，而先传递用户信息，是先告诉微服务，用户已经登录了，然后才是验证用户的身份能否访问指定的路径。但实际上，这种设计方式并不符合快速失败原则，因为checkAuth一旦失败，上文的exchange.mutate()就毫无意义，这会导致不必要的业务操作，虽然对性能影响微乎其微，但不符合设计规范

现在对网关验证有了初步认识，接下来我们研究一下其他的微服务是如何获取并验证用户信息的。在黑马商城项目中，我们为每个业务微服务定义了一套基于拦截器Interceptor的身份验证方式，即通过拦截器获取请求投中的用户信息，然后通过ThreadLocal添加到线程变量中，供下游调用。而由于所有的业务微服务都需要这个拦截器，因此我们直接将拦截器定义到了公共模块中，每个微服务只需要引入公共模块，然后依赖SpringBoot的自动装配，就可以在不写任何额外代码的情况下获取用户信息

```java
package com.tianji.authsdk.resource.interceptors;

import com.tianji.auth.common.constants.JwtConstants;
import com.tianji.common.utils.UserContext;
import lombok.extern.slf4j.Slf4j;
import org.springframework.web.servlet.HandlerInterceptor;

import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;

@Slf4j
public class UserInfoInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) throws Exception {
        // 1.尝试获取头信息中的用户信息
        String authorization = request.getHeader(JwtConstants.USER_HEADER);
        // 2.判断是否为空
        if (authorization == null) {
            return true;
        }
        // 3.转为用户id并保存
        try {
            Long userId = Long.valueOf(authorization);
            UserContext.setUser(userId);
            return true;
        } catch (NumberFormatException e) {
            log.error("用户身份信息格式不正确，{}, 原因：{}", authorization, e.getMessage());
            return true;
        }
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response, Object handler, Exception ex) throws Exception {
        // 清理用户信息
        UserContext.removeUser();
    }
}
```

定位到UserInfoInterceptor，先获取请求头中的用户信息，然后判断信息是否正确，最后按解析结果选择放行，这套流程与先前我们学习的基本相同。

```java
@Override
//    @Transactional(isolation = Isolation.REPEATABLE_READ)
public PageDTO<LearningLessonVO> pageQuery(PageQuery pageQuery) {
    // 健壮性判断
    if (pageQuery == null)
        throw new BadRequestException("分页参数不能为空");
    // 获取用户信息
    Long userId = UserContext.getUser();
    if (userId == null)
        throw new UnauthorizedException("无法获取到用户信息");

    // 执行第一次查询，查询所有课程数量
    Long count = lessonMapper.countByUserId(userId);
    // 如果课程数量为0，则直接返回
    if (count == 0)
        return new PageDTO<>(0L, 1L, List.of());
    // 计算OFFSET
    Long offset = (long)(pageQuery.getPageNo() - 1) * (long)pageQuery.getPageSize();
    // 计算可能的最大页码
    int maxPageNo = (int) (count % pageQuery.getPageSize() == 0 ?
            count / pageQuery.getPageSize() :
            count / pageQuery.getPageSize() + 1);

    // 执行第二次查询，分页查询课表
    List<LearningLesson> lessons = lessonMapper.pageQuery(pageQuery, userId, offset);
    if (lessons == null || lessons.isEmpty())
        return new PageDTO<>(0L, 1L, List.of());

    // 获取各个课程的id
    Set<Long> courseIds = lessons.stream().map(LearningLesson::getCourseId).collect(Collectors.toSet());
    // 使用课程id查询课程信息
    List<CourseSimpleInfoDTO> courseInfos = courseClient.getSimpleInfoList(courseIds);
    if (courseInfos == null || courseInfos.isEmpty()) {
        log.error("课程信息不存在，请检查课程id");
        throw new BizIllegalException("课程信息不存在");
    }
    // 将courseInfos转换为Map<id, CourseSimpleInfoDTO>
    Map<Long, CourseSimpleInfoDTO> courseInfoMap = courseInfos.stream().collect(Collectors.toMap(CourseSimpleInfoDTO::getId, c -> c));
    // 创建List<LearningLessonVO>
    List<LearningLessonVO> list = new ArrayList<>(lessons.size());
    // 遍历lessons，插入数据
    for (LearningLesson lesson : lessons) {
        // 插入课表数据
        LearningLessonVO learningLessonVO = BeanUtils.copyBean(lesson, LearningLessonVO.class);
        // 获取课程信息
        CourseSimpleInfoDTO courseInfo = courseInfoMap.get(lesson.getCourseId());
        // 插入课程信息
        learningLessonVO.setCourseName(courseInfo.getName());
        learningLessonVO.setCourseCoverUrl(courseInfo.getCoverUrl());
        learningLessonVO.setSections(courseInfo.getSectionNum());
        // 插入list
        list.add(learningLessonVO);
    }
    // 返回结果
    return new PageDTO<>(count, (long) maxPageNo, list);
}
```

业务逻辑较长，我们来仔细分析一下。首先判断查询参数是否为空，然后获取用户信息。如果无法获取到用户信息，则说明网关没有传递，或者网关权限验证被绕过，因此需要立即阻拦。然后进行两次查询，第一次查询负责计算总条数，第二次再查询实际的数据体。如果第一次查询获取到的最大数量为0，则直接返回；然后计算SQL需要的OFFSET，这里没有使用PageHelper分页插件，因此需要我们自定义分页逻辑。然后计算可能的最大页码，因为前端需要最大页码来渲染分页条。一切无误后，开始进行第二次查询，第二次查询获取课表数据，如果课表数据为空，则直接返回。然后从课表数据中获取每个课程id，根据课程id获取其详细信息，获取到详细信息后，转换为一个Map，再遍历先前获取的课表信息，将课程信息与课表信息整合，最后返回即可

可以看到，LearningRecordFormDTO并不直接对应LearningRecord，我们先理清提交学习记录的逻辑。在后端接收请求后，需要先判断数据库中是否存在该章节的记录，如果已经存在记录，则应该更新而不是新增。对于更新，先判断章节类型，天机学堂的课程章节设置为了考试和视频两个类型，如果是考试，则不需要记录播放时间等等，直接记录章节完成即可，因为考试的学习记录是在试卷提交时发送的，所以不需要考虑设置为完成后，考试由于某些原因退出后，从而导致数据库中已完成，但实际未完成的现象。而视频就是根据提交的视频总时长duration与moment进行计算，我们设置为当moment大于duration的二分之一时，则认为章节已经完成，数据库中应更新finished和finish_time字段；如果该视频已经是完成状态，则只更新学习记录表中的视频进度即可。最后再更新课表

对于新增数据，同样先判断是否符合是否是考试，如果为考试，则直接完成，设置视频进度为0。然后计算视频类型的学习记录是否达标，再插入数据库中，最后更新课表

```java
@Override
@Transactional
public void commitLearningRecord(LearningRecordFormDTO form) {
    // 判断提交数据为空
    if (form == null)
        throw new BadRequestException("提交数据不能为空");
    // 获取请求参数
    Long lessonId = form.getLessonId();
    if (lessonId == null)
        throw new BadRequestException("课表id不能为空");
    Long sectionId = form.getSectionId();
    if (sectionId == null)
        throw new BadRequestException("小节id不能为空");
    Integer sectionType = form.getSectionType();
    if (sectionType == null)
        throw new BadRequestException("小节类型不能为空");
    if (!Objects.equals(sectionType, 1) && !Objects.equals(sectionType, 2))
        throw new BadRequestException("小节类型错误");
    LocalDateTime commitTime = form.getCommitTime();
    Integer duration = form.getDuration();
    if (duration == null)
        throw new BadRequestException("视频时长不能为空");
    Integer moment = form.getMoment();
    if (moment == null)
        throw new BadRequestException("视频播放位置不能为空");
    // 获取用户信息
    Long userId = UserContext.getUser();
    if (userId == null)
        throw new UnauthorizedException("无法获取用户信息");

    // 尝试从数据库中查询该记录
    LearningRecord record = learningRecordMapper.queryLearningRecord(lessonId, sectionId, userId);
    // 记录是否有章节完成
    int finished = 0;
    // 如果有记录，则更新该记录
    if (record != null) {
        // 如果是考试，直接返回
        if (Objects.equals(sectionType, 2))
            return;
        // 设置新的播放时间
        record.setMoment(moment);
        // 如果没有完成
        if (!record.getFinished()) {
            // 如果播放时间已经超过总时长的50%，则认为章节已完成
            record.setFinished(duration - moment < moment);
            // 如果第一次完成，则设置完成时间
            if (record.getFinished()) {
                // 设置完成时间
                record.setFinishTime(commitTime);
                finished = 1;
            }
        }
        // 更新记录
        learningRecordMapper.updateById(record);
    } else {
        // 如果没有记录，则插入一条新的记录
        record = LearningRecord.builder()
                .id(IdWorker.getId())
                .lessonId(lessonId)
                .sectionId(sectionId)
                .userId(userId)
                .build();
        // 如果是考试，则立即完成
        if (Objects.equals(sectionType, 2)) {
            record.setMoment(0);
            record.setFinished(true);
            record.setFinishTime(commitTime);
            finished = 1;
        } else {
            // 不是考试，则按照播放位置判断完成
            record.setMoment(moment);
            record.setFinished(duration - moment < moment);
            record.setFinishTime(record.getFinished() ? commitTime : null);
            finished = record.getFinished() ? 1 : 0;
        }
        // 插入记录
        learningRecordMapper.insert(record);
    }
    // 更新课表
    LearningLesson lesson = lessonService.getById(lessonId);
    LearningLesson newLesson = LearningLesson.builder()
            .id(lessonId)
            .latestSectionId(sectionId)
            .latestLearnTime(commitTime)
            .learnedSections(lesson.getLearnedSections() + finished)
            .build();
    Integer update = lessonService.updateById(newLesson);
    if (!Objects.equals(update, 1))
        throw new DbException("更新课表失败");
}
```

对于这个方法，有一些需要注意的点。首先是需要使用一个finished来记录是否有完成事件，因为课表中需要维护一个learnedSections字段，只有当完成事件发生时才允许learnedSections自增，而完成事件不能通过record本身的getFinished来判断，因为在更新时，有些record的getFinished字段可能已经为true，而如果按照getFinished来判断，则会导致每一个已经完成的视频进度提交时，都会让课表中的learnedSections自增。因此我们设计了int finished = 0来维护完成事件，只有当第一次完成时才加一，让课表更新时能够自增

同时，这里对于完成度的计算并不直接基于浮点数，计算机浮点运算永远存在误差，所以我们直接基于整型运算，通过duration - moment < moment来判断播放是否达标，只有当剩下的视频进度小于已经播放的进度时，才认为学习已经达标

不过这个接口的远程调用相当多，数据库调用也很多，而且这还是一个常用接口，视频在播放时就会大量自动提交，因此在后续的学习中，我们可以考虑对这个接口进行性能优化

```java
}
```

本周完成总数是最难计算的，我们先声明一个外部变量weekFinished，然后遍历所有课程，这里最麻烦的其实是黑马并没有提供课程id与章节id的直接映射，有这张表，但是没有这个接口。如果想要获取一个课程的全部章节id，则只能通过课程id获取课程的全部信息实体，从实体中获取章实体，最后再获取节实体，并获取节id，黑马也没有提供批量查询接口，导致这里必须进行RPC调用，严重影响查询性能。

回到代码中，我们定义了本周已学节数和总已学节数。通过判断学习计划中的每个完成时间，如果在本周，则两个都自增，如果不在本周，则只有总已学节数自增。然后获取课程详细信息，这里只能调用一个单次查询接口，所以必须事先遍历课程id。如果无法获取课程详细信息，则直接抛出异常。然后从课程实体中利用stream流获取节信息，再遍历节，获取节id，通过节id从学习记录表中获取每个节的学习情况，根据完成时间判断是否为本周学完的，如果是，则自增weekFinished和weekLearnedSections，需要注意weekFinished是用户本周完成的节总数，而weekLearnedSections是每个课程的周完成节计数。全部计算完成后，构建每个课程的LearningPlanVO

最后的逻辑与之前相同，进行内存分页，然后封装数据并返回。这里不使用数据库分页是因为数据库分页无法实现我们需要的逻辑，课表表中并没有记录每个章节的完成状况，如果使用数据库分页，则无法得知哪些课程在本周存在学习记录。这里不能通过最近学习时间来判断，因为已经完成的章节再次学习后，同样会记录最近学习时间；而且返回的数据中需要记录学习的总进度，要么按照课程查询每个课程的所有学习记录，要么查询所有学习记录，再按照课程id进行分组。在给妈商城项目中，课程记录相对较少，因此我们选择后者

根本原因就是缺乏课程id与章节id的直接映射接口，导致我们只能通过
$$
课表 \Rightarrow 课程id \Rightarrow 课程详细信息 \Rightarrow 章 \Rightarrow 节 \Rightarrow节id
$$
这样的方式来间接获取节id，增加了大量的中间过程

### 高并发优化

在黑马商城项目中，学习进度的记录是由前端每15秒发送一个POST请求到后端，或者当用户手动点击播放进度时，也会提交一个POST请求到后端，来存储提交的视频播放进度。而在相应的提交学习记录接口中，存在大量的数据库操作，如learningRecordMapper.queryLearningRecord(lessonId, sectionId, userId)、learningRecordMapper.updateById(record)、learningRecordMapper.insert(record)，以及远程调用操作lessonService.getById(lessonId)。在高并发情况下，这会造成大量的性能损失，假设有十万用户同时播放视频，默认每15秒记录一次播放进度，那么理论上单个用户每秒产生的请求数为$1 \div 15 \approx 0.0666667$，十万用户总计QPS大约为6667。一般来说，一台4C8G的服务器部署Spring项目，能够承载的常规后端服务QPS为500，最大800，如果需要承载6667QPS，则至少需要14台服务器。对于常规企业而言，这完全是不可接受的，因此需要进行优化

一般来说，高并发优化分为三个方向。第一，提高单机并发，尽可能减小业务接口的RT（响应时间 ResponseTime），提升单机性能和并发能力；第二，水平扩展，将热点服务水平扩展，做好负载均衡，提高集群并发能力；第三，服务保护，做好服务熔断、服务降级保护措施，提高服务的高可用性。水平扩展和服务保护一般是基于业务架构进行操作，而作为代码开发人员，我们能实施的目前只有提高单机并发

而提高单机并发，也就是提升单机的读写性能，读性能可以通过优化代码、SQL以及设置缓存来提升，而写性能除了优化代码、SQL外，还可以将同步写改为异步写，以及合并写请求

**异步写**

异步写是指将原本的同步写操作基于消息队列改为异步执行。假设接口A需要调用三个数据库写操作，每个写操作耗时100ms，那么接口总耗时就是300ms，属于较慢的RT。而如果我们不直接调用每个数据库写操作，而是发送一条MQ消息，然后由三个数据库写接口自己接收消息并消费，那么对于用户端来说，RT就可以缩短为接口调用到消息发送的总时长，远远小于300ms

对于异步写，优点是无需等待，大大减少RT；而且可以利用MQ暂存消息，进行流量削峰整型；同时降低写频率，减轻数据库并发压力。而缺点也很明显，需要依赖MQ可靠性，没有减少数据库写次数，仅仅是降低频率

**合并写**

合并写是指利用缓存的高性能，在进行数据库写操作时不直接写进数据库，而是写进数据库缓存中，再定义一个定时任务，从数据库缓存中提取写数据，再将数据一并写入数据库中。继续使用上文的例子，这次不再发送MQ消息，而是将数据写入Redis等缓存数据库中，然后额外定义一个定时任务，从Redis中获取需要写入的数据，再一次性写入数据库中，减少数据库写操作

合并写的优点是写缓存速度快，可以大大减少响应时间；同时降低了数据库写频率和写次数，减轻数据库并发压力。而缺点是实现相对复杂，而且强依赖缓存系统可靠性，并且不支持事务和复杂业务

#### 提交学习记录接口优化

首先对播放进度提交的代码进行一些复习，这里就只粘贴核心片段

```java
// 尝试从数据库中查询该记录
LearningRecord record = learningRecordMapper.queryLearningRecord(lessonId, sectionId, userId);
// 记录是否有章节完成
int finished = 0;
// 如果有记录，则更新该记录
if (record != null) {
    // 如果是考试，直接返回
    if (Objects.equals(sectionType, 2))
        return;
    // 设置新的播放时间
    record.setMoment(moment);
    // 如果没有完成
    if (!record.getFinished()) {
        // 如果播放时间已经超过总时长的50%，则认为章节已完成
        record.setFinished(duration - moment < moment);
        // 如果第一次完成，则设置完成时间
        if (record.getFinished()) {
            // 设置完成时间
            record.setFinishTime(commitTime);
            finished = 1;
        }
    }
    // 更新记录
    learningRecordMapper.updateById(record);
} else {
    // 如果没有记录，则插入一条新的记录
    record = LearningRecord.builder()
            .id(IdWorker.getId())
            .lessonId(lessonId)
            .sectionId(sectionId)
            .userId(userId)
            .build();
    // 如果是考试，则立即完成
    if (Objects.equals(sectionType, 2)) {
        record.setMoment(0);
        record.setFinished(true);
        record.setFinishTime(commitTime);
        finished = 1;
    } else {
        // 不是考试，则按照播放位置判断完成
        record.setMoment(moment);
        record.setFinished(duration - moment < moment);
        record.setFinishTime(record.getFinished() ? commitTime : null);
        finished = record.getFinished() ? 1 : 0;
    }
    // 插入记录
    learningRecordMapper.insert(record);
}
// 更新课表
LearningLesson lesson = lessonService.getById(lessonId);
LearningLesson newLesson = LearningLesson.builder()
        .id(lessonId)
        .latestSectionId(sectionId)
        .latestLearnTime(commitTime)
        .learnedSections(lesson.getLearnedSections() + finished)
        .build();
Integer update = lessonService.updateById(newLesson);
if (!Objects.equals(update, 1))
    throw new DbException("更新课表失败");
```

首先尝试从数据库中查询该记录，如果存在记录，则应当更新记录，而不是插入新记录。注意这里维护了一个int finished来记录本次提交是否有学习状态变更，因为针对课表的更新是统一进行的，课表在更新时需要得知当前提交记录是否需要将已学节数进行自增。进入更新逻辑，首先判断是否为考试，如果是考试，则应当直接返回，其实理论上来说并不存在考试进度二次提交的问题，因为考试记录的提交只会在考试交卷时进行，而天机学堂中每个考试只能进行一次，用户对于每个考试仅有一次考试记录提交的机会，这一次一定是新增记录。但后端同样需要进行过滤，以避免恶意请求导致的存在多个考试记录的问题。

然后设置新的播放时间，再判断该记录是否已经完成过，如果没有完成过，则需要根据播放时长计算是否完成。如果是第一次完成，则应该设置完成时间，并设置已完成加一，最后更新记录

而高并发优化的目标正是这个更新操作，插入操作每个用户只会完成一次，所以不需要额外优化。对于这个更新接口，我们可以利用合并写来进行优化，合并写相较于异步写性能更加优越，而且在更新逻辑中，更新操作与业务强相关，不应使用MQ强行解耦

**Redis数据结构**

确定了合并写方案，还需要确定Redis中存取哪些数据，我们可以根据业务需求来进行分析。最重要的就是用户的播放进度moment，而播放进度需要对应一个课程小节，所以还需要sectionId，而学习记录表中可能存在不同用户的相同课程的学习进度，因此我们还需要一个字段来区分不同的用户，这里就不使用userId，而是lessonId。详细数据结构如下

| KEY      | HashKey   | HashValue                           |
| -------- | --------- | ----------------------------------- |
| lessonId | sectionId | {id: 1, moment: 1, finished: false} |

设置这样的数据结构，是为了在进行查询时也可以直接查询缓存中的数据，而不需要向数据库发送请求。首先用户提交学习记录，然后后端从缓存中查询当前用户的学习记录，如果不存在，则向数据库申请，如果数据库中也不存在，则认为用户第一次提交记录，直接请求数据库即可。如果数据库中存在，则使用数据库中的数据继续；然后判断是否是第一次学完，如果已经学过，则直接将进度更新到缓存中，然后返回。如果还没学完，则根据视频进度判断是否第一次学完，没学完的，与已经学过的相同路径，更新视频进度，然后返回；对于第一次学完的，立即更新数据库中的学习状态，并删除对应缓存，保证数据一致性

而合并写就是针对于已经完成的和第一次没有完成的，一般的合并写操作是定义一个定时任务，周期性地从缓存中获取数据，并执行数据库更新操作。但在我们的接口这会存在一个问题，假设一个视频长度300秒，用户每观看15秒就会发送一个记录请求，假设用户从第151秒断开，目前已经提交了10次请求，却只有最后一次请求属于有效请求，这会白白浪费9次数据库更新操作。因此，数据库更新的时期不应该是定期的，而是用户离开的时刻，而用户离开后最明显的特征就是时长不再发生变化，或者不再有请求提交到后端。我们设置的每15秒提交一个请求，假设用户已经20秒没有再提交新的请求，那么我们就可以认为，用户已经没有再播放视频，就可以执行数据库插入操作了。而这里就需要利用延迟任务来实现了

#### 延迟任务

延迟任务是指任务发起者申请的一个需要延迟执行的任务，延迟任务的执行相对于任务发起者是异步的，不应阻塞发起者的任务执行。目前主流的延迟任务方案有四类，如下：

- DelayQueue：JDK自带的延迟队列功能，存入队列的元素可以指定延迟执行的时间
- Redisson：基于Redis数据结构模拟的JDK的DelayQueue，相较于JDK原生DelayQueue可以减轻内存负担
- MQ：基于消息队列的延迟消息实现延迟任务，一些MQ本身就支持延迟消息，如RocketMQ
- 时间轮：基于时间轮算法实现的延迟任务或者定时任务，但是需要开发者自己实现，或者利用现成的如Netty中，有开源的实现

针对天机学堂的提交学习记录接口，我们直接利用最简单的DelayQueue来实现

**示例**

创建一个DelayedTask，实现Delayed接口，需要实现getDelay和compareTo两个方法

```java
package com.tianji.learning.task;

import java.util.concurrent.Delayed;
import java.util.concurrent.TimeUnit;

public class DelayedTask implements Delayed {
    @Override
    public long getDelay(TimeUnit unit) {
        return 0;
    }

    @Override
    public int compareTo(Delayed o) {
        return 0;
    }
}
```

getDelay用于获取剩余时间计数，compareTo用于比较哪个任务剩余时间更多

```
package com.tianji.learning.task;

import lombok.AllArgsConstructor;
import lombok.Data;

import java.util.concurrent.Delayed;
import java.util.concurrent.TimeUnit;

@Data
@AllArgsConstructor
public class DelayedTask<D> implements Delayed {

    private D data;

    private final long startTime = System.nanoTime();
    private final long delay;

    @Override
    public long getDelay(TimeUnit unit) {
        return unit.convert(startTime +  delay - System.nanoTime(), TimeUnit.NANOSECONDS);
    }

    @Override
    public int compareTo(Delayed o) {
        return (int) (this.getDelay(TimeUnit.MILLISECONDS) - o.getDelay(TimeUnit.MILLISECONDS));
    }
}
```

对于getDelay，我们通过在构建对象时，使用System.nanoTime()获取当前系统时间，也就是开始时间，然后传入参数delay，计算startTime + delay就可以获取任务结束时间。调用getDelay时，只需要通过结束时间减去当前时间即可得到剩余时间

现在我们定义一个测试类，编写三个测试任务，设置任务延迟时间分别为5s、3s、1s

```java
package com.tianji.learning.task;

import lombok.extern.slf4j.Slf4j;
import org.junit.jupiter.api.Test;

import java.util.concurrent.DelayQueue;

@Slf4j
class DelayedTaskTest {
    @Test
    void test() throws InterruptedException {
        // 声明一个延迟任务队列
        DelayQueue<DelayedTask<String>> queue = new DelayQueue<>();
        // 向队列中添加任务
        queue.add(new DelayedTask<>("task1", secToNano(5)));
        queue.add(new DelayedTask<>("task2", secToNano(3)));
        queue.add(new DelayedTask<>("task3", secToNano(1)));
        // 获取任务
        log.info("开始获取任务");
        while (!queue.isEmpty()) {
            log.info("获取任务：{}", queue.take().getData());
        }
    }

    private static long secToNano(int seconds) {
        return seconds * 1000 * 1000 * 1000L;
    }
}
```
